## Part 2: Fine-Tuning vs. Agentic RAG — The Critical Architectural Decision

This is the most important decision you'll make, and getting it wrong is how hallucination enters the system. The rule is simple:

> **Fine-tune on data that teaches the model *how to reason* about your domain. Use RAG for any data point that has a timestamp on it.**
> 

Here's the exact split for your data stack:

**Bake into weights via Fine-Tuning (Static Domain Knowledge):**

- Population data (Census, projections)
- State Finance Budgets (Karnataka, TN, Maharashtra, etc.) — these teach the model how government expenditure patterns correlate with business opportunity
- Election data (for understanding political economy of specific talukas)
- Dam levels (historical patterns for agricultural feasibility)
- Police/Crime PDF data (for risk scoring)
- Scheme eligibility frameworks (PMAY, Jal Jeevan — the *structure* of schemes, not live disbursement status)
- Court jurisdiction and transport network structure

The fine-tuning here isn't about memorizing facts. It's about teaching the model how a feasibility report *reasons* — "high rainfall + low competitor density + active PMAY coverage = favorable market entry for building materials retail."

**Must be fetched at Runtime via Agentic RAG (Live/Volatile Data):**

- Current commercial rental prices (MagicBricks, 99Acres, NoBroker — prices shift monthly)
- Existing business counts and ratings from Justdial/Sulekha (new businesses open every week)
- Live crop prices (daily volatility)
- Current weather and rainfall data
- RSS feeds for infrastructure and scheme updates
- Any real estate pricing from any source

If your model has a rental price for Koramangala baked into its weights from your training run, and that report is generated 8 months later, the price is wrong and your credibility is gone. This is non-negotiable.

## Part 3: Step-by-Step Architecture Blueprint

The diagram above represents the full pipeline. Here's what each layer actually does and why it's designed that way.

**Step 1 — Query Router.** Before any model inference happens, extract structured metadata from the user query: location (ideally down to taluka/ward level), business sector, and report type (new entry, competitor analysis, land use feasibility). This is a lightweight classifier — a fine-tuned BERT or even a regex + NER pipeline works fine here. You do not want your 70B model burning compute on this.

**Step 2 — Trigger parallel data fetchers.** Based on the extracted location and sector, simultaneously fire off: your real estate scrapers (MagicBricks, NoBroker for that pin code), your Justdial/Sulekha competitor pull for that category and radius, live crop price API if agricultural correlation is relevant, weather/rainfall API, and any applicable RSS infrastructure feeds. All fetched chunks get tagged immediately with source name, URL, and a UTC timestamp. This timestamp is what kills hallucination at the source — the model never encounters a price without knowing it's from yesterday.

**Step 3 — Vector index retrieval.** Your live data is chunked, embedded (use `nomic-embed-text` or `bge-m3` — both run on free-tier infra), and stored in a vector store. Qdrant hosted or pgvector on Supabase are both free-tier compatible with your stack. The retriever pulls the top-k most relevant chunks for the specific query. Apply a metadata filter here — only return chunks where the geographic tag matches the queried district. This is critical: you do not want Mumbai rental data leaking into a Mysore report.

**Step 4 — Context assembly with citation tags.** Before the retrieved chunks enter the prompt, wrap every single chunk in a citation tag:

```
[SOURCE: MagicBricks | LOC: Whitefield, Bangalore | DATE: 2025-07-14]
Commercial retail space, 800 sqft: ₹45,000/month
[/SOURCE]
```

This isn't decoration. It's machine-readable provenance that the verifier in Step 6 uses to check claims.

**Step 5 — Structured prompt with hard grounding constraints.** The system prompt must be explicit and non-negotiable:

> "You are a business feasibility analyst. You must use ONLY the data provided in the [CONTEXT] blocks below. If a specific data point is not available in the context, write 'Data not available for this location' — never estimate, interpolate, or use general knowledge for any numerical claim. Every figure you state must be traceable to a [SOURCE] block."
> 

Output format should be constrained to JSON with a specific schema: each claim object contains a `value`, a `source_id` referencing the tagged chunk, and a `confidence` flag. This makes the verifier's job trivial.

**Step 6 — The Hallucination Firewall.** This is your product's core IP. After the model outputs its JSON report draft, a programmatic verifier scans every numerical claim against the source chunks. If a claim cannot be string-matched or semantically matched back to a [SOURCE] block, it gets either blocked (replaced with "Data unavailable") or flagged with a low-confidence indicator. This is not another LLM call — it's deterministic code. A second, smaller model (Llama 3.1 8B) can serve as a cross-checker for semantic verification if exact string matching is insufficient, but the primary gate should be rule-based for latency reasons.

**Step 7 — Report rendering.** The final output renders each section with its citation visible to the user — not buried in footnotes, but inline, like: "Commercial rent in Koramangala 5th Block averages ₹52,000/month for 600 sqft *(MagicBricks, fetched Jul 14 2025)*." This is the visible proof of your system's integrity.

## Critical Warnings for Your Specific Stack

Three failure modes you must design against from day one:

**Geographic bleed** is when your vector retriever returns chunks from the wrong city because the embedding space conflates similar-sounding areas. Mitigation: always apply a hard metadata filter on district/state before semantic search, not instead of it.

**Stale static data** will eventually become a problem even in your "baked" layer. Run quarterly fine-tuning refresh cycles on budget and population data, and version your model checkpoints by training date. When a user asks about a scheme, the report should state the scheme data version, not just cite "government data."

**The real estate aggregator problem** is that MagicBricks and 99Acres often have wildly inconsistent data for tier-2 and tier-3 cities — sparse listings, inflated ask prices. Build a data quality scorer that flags low-confidence real estate sections when fewer than 3 independent listings exist for a given area. Display this uncertainty explicitly in the report rather than presenting a single listing as market-rate truth.
